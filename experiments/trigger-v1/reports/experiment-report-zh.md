# Skill 提取链路实验报告

## 结论

推荐链路是 `sop_v1 边界候选 → precision_v1 价值门 → balanced_v4 reviewer → 去重/版本化写入`。固定 10 次工具调用不适合短 SOP；每个 turn 都问模型又太贵。确定性边界做主路径、LLM judge 做不确定带 shadow，能在精度、召回、成本和可解释性之间取得更稳的平衡。

## 1. 何时到达提取候选时机

比较了五类办法：

| 方法 | 优点 | 主要问题 | 本轮证据 |
|---|---|---|---|
| 固定工具调用次数 | 简单、零模型成本 | 与 SOP 长度无关，短任务漏、长任务切碎 | 固定 10 次召回 0；固定 2 次精度仅 50% |
| 字节/轮次硬上限 | 防止无限缓冲 | 只能是安全阀，不表达语义完成 | 保留为 hard cap |
| 当前/上次是否同一 SOP | 能在新任务进入前切旧任务 | 只判断换题会漏掉会话自然结束 | 实现 `before_append`，新 batch 留给下一 SOP |
| 完成/验证信号打分 | 确定、低成本、可解释 | 隐式表达召回有限 | `sop_v1` P=100%、R=73.3%、F1=84.6% |
| LLM 边界判断 | 能理解隐式完成和同义换题 | 成本、时延、漂移、注入风险 | P/R/F1=93.3%，只需候选调用 21/79 |

边界评测共 24 个基础 case、79 个 batch、15 个正边界；另有 96 个噪声/确认/合并/拆分变形 case。变形集上确定性结果不变，说明批次扰动没有破坏当前规则，但这些样本相关，不作为独立统计证据。

## 2. 时机到了，仍可能不提取

`precision_v1` 是 reviewer 前的高置信过滤器：秘密、明确不留存、未解决失败、纯解释/无执行琐事直接跳过；灰区继续交给 reviewer。44 个平衡 case 上，它避免了 16 次 LLM 调用（36.4%），skip precision 100%，正例透传 recall 100%，没有 unsafe false skip。

最终标准不是“尽量多存”或“尽量少存”，而是最大化净复用效用：

`未来复用收益 × 证据可信度 × 适用范围 − 错误迁移风险 − 上下文/维护成本`

应写入的包括验证过的多步 SOP、高成本排障、稳定偏好和环境约束；不应写入的包括一次性答案、未经验证的猜测、秘密、用户拒绝留存以及与现有 Skill 等价的重复内容。后两类要通过去重、update/patch 和版本历史处理，而不是创建更多文件。

## 3. 如何提取高质量 Skill

Reviewer 必须先 `list/view` 再决定 `create/update/patch/nothing`，并要求：明确触发条件、前置条件、参数化步骤、验证方法、失败分支、禁止项、适用范围、证据与敏感信息清理。v3 精度 prompt 把误提取降下来了，但 calibration recall 只有 66.7%；v4 补回偏好、背景事实、隐式验证和换题场景。

在 v4 调整后冻结的 30-case holdout 上，legacy_v2 为 P=75%、R=100%、F1=85.7%、误提取率 33.3%、质量 86.9；balanced_v4 为 P/R/F1=100%、误提取 0、质量 100。v4 prompt tokens 为 123,235，相对 legacy 的 287,733 减少约 57.2%。这些结果用于选型，不应解读为总体真实流量已经达到 100%。

小样本的不确定性必须显式报告：按 95% Wilson 区间，15/15 的成功率下界约 79.6%，0/15 的错误率上界约 20.4%；`sop_v1` 的 11/15 边界召回区间也很宽。因此门槛判断应看点估计与区间，而不是把 100% 当作已证明的生产承诺。

## 4. 实现落地

- 新增 `legacy/sop_v1` trigger profile，默认仍是 legacy，避免无意改变线上行为。
- `before_append` 先归档旧 SOP，当前新任务进入新缓冲；`after_append` 处理已验证完成。
- 新增 `legacy/precision_v1` value gate；只有确定负例跳过 LLM。
- Reviewer 支持 `legacy_v2/precision_v3/balanced_v4` 可配置选择。
- 工具数与字节阈值继续作为不可失效的安全上限。
- 新增 16 个单元/集成测试，覆盖边界分数、换题前归档、完成后归档、价值门安全负例和正例透传。

## 5. 测评真实性与陷阱

本轮主动修正了一个关键计分问题：`after(i)` 与 `before(i+1)` 是同一切点，必须规范化，否则会把等价预测算错。还需要防范：数据泄漏、同母样本伪独立、类别平衡与生产先验不一致、只看 F1 忽略负迁移、LLM judge 自评偏差、模型/温度漂移、重复 Skill 造成的表面召回、失败任务被误当成功，以及只测提取、不测后续复用。

上线验收必须增加 end-to-end 指标：任务 pass@1、Skill 命中后 turn/token 变化、错误迁移率、重复率、更新率、人工撤销率、30/60/90 天复用率与每次有效复用成本。

另外跑了 6 个真实 WorkBuddy 本地编码修复 smoke case（每个都实际执行 `node --test`）：6/6 通过，但日志可观测到的 archive trigger 只有 1/6，Skill 新增 0。这个结果不能与人工边界集直接合并，却揭示了更重要的外部有效性问题：通用运维语料上的完成信号不能直接覆盖 coding-agent 的结束表达。它支持“先 shadow、继续扩真实轨迹”，不支持现在把 `sop_v1` 设成生产默认。完整记录见 `experiments/baseline/results/task2-sop_v1.json`。

## 6. 发布建议

1. 离线采用 `sop_v1 + precision_v1 + balanced_v4` 作为候选组合，固定数据哈希与 prompt/model 版本；coding 轨迹补齐前不宣称已通过生产门槛。
2. 线上第一阶段只 shadow：记录候选切点、价值门决策和 LLM judge，不创建 Skill。
3. 第二阶段 5% canary 自动写入，但只允许高置信 `create/update`，保持一键回滚到 legacy。
4. LLM judge 只处理确定性分数不确定带或隐式完成候选；超时 fail-open 到继续缓冲，最终由 hard cap 收口。
5. 每周抽样误提取、漏提取和负迁移；按错误簇补充测试集，而不是围绕单个 case 改规则。
